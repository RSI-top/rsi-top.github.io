A stalled search, and the way out

Main contributions

  • We characterize exploration collapse in long-horizon autoresearch. The agent's proposals narrow onto a single direction: it keeps refining the same idea while the best score stops improving, like gradient descent trapped in a local minimum. In our runs, the frontier is stalled for 84% to 92% of the time.
  • A metric dashboard for long histories. htop gives you an at-a-glance view of process activity and resource usage, helping you decide where to look before digging into logs. RSI-top builds the same view for an autoresearch run: it summarizes each trajectory using task-specific metrics defined before the run and computed in the background.
  • Diversity-controlled interventions. When the frontier goes flat, RSI-top steps in with a cohort of agents and encourages them to explore different fixes: each reads a different subset of the dashboard, proposes a portfolio of directions with verbalized probabilities, and grounds those directions in different lineages of the shared search history.
  • A plug-in harness. RSI-top adds interventions around an existing framework's search loop (e.g., OpenEvolve, ShinkaEvolve) while leaving its internal selection and mutation rules unchanged.

Why long autoresearch runs stall

The autoresearch loop

An autoresearch run is a sequence of experiments organized by parent–child relationships. In each iteration, the agent picks an earlier candidate as the parent, proposes a change, implements it, and ends with a new candidate, for example a kernel or a checkpoint. An evaluator scores the candidate, and the result joins the archive that later iterations build on. We call the full record of one iteration a trajectory: the agent's reasoning trace, the actions and code changes it made, and the execution and evaluation logs. A run makes hundreds of these trajectories over many hours. The best score found so far is what we call the frontier.

What exploration collapse looks like

Think of the search as gradient descent on a landscape of ideas, where height is the loss: lower is better. Early on, progress comes easily. Then the agent settles into one valley and keeps running experiments in the same narrow direction, so the frontier stops moving. Its proposals collapse onto a narrow family of approaches. Only when the frontier stalls does RSI-top step in: it launches a diverse cohort to explore alternative directions, adds the resulting candidates to the archive, and lets the native search continue.

Real runs spend most of their time stalled

We ran OpenEvolve and ShinkaEvolve on Anthropic kernel optimization, each with DeepSeek v4 Flash and Gemini 3.7 Flash. All four runs follow the same pattern: after early gains, the frontier is stalled for 84% to 92% of the run.1 We use frontier stalls to trigger interventions; a stall alone does not establish that exploration has collapsed.1A stall is any stretch of at least 20 minutes, after the first hour of the run, in which the best score improves by fewer than 2 cycles.

Stuck in its own history

Why does the agent get stuck? One likely contributor is context inertia: the model commits to a direction in its context and keeps pursuing it after the evidence says to change course. Every attempt in that direction adds to the context that pulls the next attempt along.

Yet the agent cannot simply ignore its history. To leave a valley, it needs to know what was tried, what helped, and which branches still look promising, and after hundreds of trajectories that history no longer fits in context anyway. The usual ways to manage the context either keep too much or throw away exactly the information an escape needs. The challenge is to retain enough information to choose what to inspect without repeatedly loading the full history. RSI-top keeps a dashboard as a comparable index of every trajectory and retrieves raw trajectories only on demand.

RSI-top: compress the history, diversify the escape

Key idea

Nobody reads every log line to see what a machine is doing. You use htop to inspect processes and resource usage, or nvidia-smi for GPUs,2 then dig into the logs that matter. RSI-top gives autoresearch the same thing: a dashboard that compresses each trajectory into a compact set of task-specific metrics. When the search stalls, agents read the dashboard, unfold the few trajectories worth a closer look, and plan an escape. We call retrieving and inspecting a full trajectory “unfolding.” Diversity control encourages different intervention plans.2htop is an interactive process viewer for Unix-like systems; nvidia-smi reports the state of NVIDIA GPUs.

  1. Design metricsAn LLM reads the task description and writes metric specs, each with a fixed input and output. Each spec is compiled into a script before the first trajectory.
  2. Score in the backgroundThe metric scripts score each finished trajectory while the agent already runs the next one. Each score adds one row of numbers to the dashboard.
  3. Detect stallsA monitor watches the frontier on the dashboard. When the best score stays flat,3 it pauses the native search and triggers an intervention.3Flat means a frontier stall: the best score stops improving significantly over a set time span. On Anthropic kernel optimization, for example, a stall is any stretch of at least 20 minutes in which the best score improves by fewer than 2 cycles.
  4. Unfold selectivelyAgents scan the metric rows instead of reading the full history. They load only the few trajectories that look most informative for escaping the current valley.
  5. Intervene, then hand backAgents propose diverse new directions, and every proposal runs in parallel as its own trajectory. After the intervention, the native search resumes.

The dashboard

The metric definitions are fixed before each run and remain unchanged throughout it. Each trajectory gets one row of numbers. That row is a compressed record of the trajectory that agents can scan, sort, and compare without loading the trajectory itself.

Diversity control

A shared dashboard alone does not ensure diverse proposals. RSI-top runs the intervention as a cohort of multiple agents and pushes them apart in three ways.4 Click each one for details.4In the default configuration, each agent sees a random 15 of the 25 metrics.

Like an ensemble whose members see different features, each agent in the cohort receives a different random subset of the dashboard's metrics. Agents that watch different signals rank the history differently, so they unfold different trajectories and reach different conclusions about where the search went wrong.

In contrast, giving every agent the same view can lead to overlapping retrieval choices and similar proposals.

Asked for one idea eight times, an LLM can return closely related variations of its most typical answer. Following Verbalized Sampling, each agent instead proposes eight directions as one portfolio, each with a verbalized probability. Each probability estimates how likely an ordinary planner would be to propose that direction independently, so a low value marks a less obvious idea. The values need not sum to 1, and they are not a calibrated chance of success. Asking for a distribution brings out credible low-probability ideas.

prompt excerpt
Generate the directions as one joint portfolio sampled across the distribution of credible interventions, not as variations of the single most typical answer. Include credible lower-probability modes as well as common modes.

Add a numeric `verbalized_probability` between 0 and 1 to every direction. [...] Directions are substantively distinct only when they test materially different bottleneck -> mechanism -> expected-effect hypotheses; changing only a target, parameter, or wording is insufficient.

Evolutionary frameworks pick a parent from the archive and build on it. Linking every trajectory to its parent turns the archive into a DAG. Each lineage is a different branch of the search history. All agents share this history; the prompt asks each agent to find distinct causal subgraphs in it and ground its directions in different ones, so the portfolio covers genuinely different opportunities.

prompt excerpt
Use selective unfolding to find as many distinct, relevant causal subgraphs as the evidence supports. Ground directions in different subgraphs when possible so the portfolio covers genuinely different opportunities.

Experiment results

We evaluate on two benchmarks where every trajectory builds on the ones before it. Anthropic kernel optimization asks the agent to optimize a kernel for a simulated machine, scored in cycles (lower is better). MLE-bench asks it to compete in Kaggle competitions, scored on a validation set during the search and then tested on the hidden test set. On Anthropic kernel optimization, we plug RSI-top into OpenEvolve and ShinkaEvolve: it adds interventions around the native search loop while leaving its internal selection and mutation rules unchanged. On MLE-bench, we plug RSI-top into a simple ReAct loop.

Anthropic kernel optimization

All four framework and model pairs follow the same pattern: the OpenEvolve or ShinkaEvolve run stalls, and RSI-top climbs out of the stall. As a reference, we also run each framework on its own, without RSI-top, with GPT-5.6 Sol and with Claude Opus 5 until a $300 API budget is spent (dashed lines). MLE-bench

RSI-top runs with Gemini 3.7 Flash on one A100 for 12 hours. Across 75 competitions, it achieves a mean medal rate of 63.1%, matching the highest reported mean among the listed methods. It produces valid submissions on all competitions and achieves the highest reported mean above-median rate (77.3%) and gold rate (43.1%). What's next

Autoresearch agents are starting to run for days, and the bottleneck is shifting from how much compute an agent gets to how it sees its own history. RSI-top is a first step: give the agent a dashboard of its own history, let it retrieve only the trajectories worth reading, and push the search in more than one direction when it stalls. We are excited about where this goes next.

  • Better context management for multi-agent autoresearch. Combining RSI-top with DeLM, where parallel agents coordinate through a shared context and a task queue, would let the dashboard serve as that shared context.
  • A dashboard for every long-running agent. The same look-then-unfold pattern applies to any agent, or team of agents, whose history outgrows its context, from coding agents to research assistants.
  • From stall-triggered to always-on. Once agents claim work asynchronously, there is no need to pause the search and wait for a stall: agents can check the dashboard continuously and steer the search before it settles into a valley.

Notes & references

Concurrent work. Several concurrent systems see long autoresearch runs plateau and fix it the same way: discard the conversation and keep the work. Fork-and-Flush [3] calls the effect "idea basins"; it forks an agent into copies that share the workspace but start with an empty context, runs them for a fixed horizon, and continues from the best copy. Scaling Discovery Requires Forgetting [4] periodically discards every agent's session and the candidate history, then restarts from the best candidate so far. Anthropic's Memento harness [5] stops each agent at a fixed timeout and hands a fresh agent the codebase and a short note. These approaches reset the conversational context and carry forward only the workspace or the best candidate. RSI-top instead keeps a structured index of prior experiments to guide selective retrieval and intervention planning, and diversifies the agents it launches.
